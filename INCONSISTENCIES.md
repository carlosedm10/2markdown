## Worth a look

- **Native `.venv` on this machine is polluted with stray `groq`/`mistralai` packages not in `uv.lock`** — `.venv/lib/python*/site-packages` had `groq==1.4.0` and `mistralai==2.10.0`/`mistralai==2.4.8`-ish installs predating the `pydantic-ai[groq,mistral]` extras fix above (installed by hand, or left over from an earlier experiment — not something `uv sync`/`uv lock` put there). This makes native (`NATIVE=1`/`CI=true`) runs an unreliable signal for "does the provider SDK actually resolve from the lockfile": the native venv can import `groq`/`mistralai` even when `uv.lock` doesn't pin them, silently passing a check that Docker (which only ever installs from `uv.lock`) would fail. Always verify provider-import behavior with the Docker transport (`make test-backend`, not `NATIVE=1 make test-backend`); `uv run` inside the container re-syncs `.venv` to the lockfile on every invocation; only Docker's `.venv` is authoritative here. The stray host packages were left in place (not `pip uninstall`ed) since this repo does not own the host Python environment and the fix is regardless bypassed for any transport that has an `.env`-independent, already-synced Docker image.

## Fixed

- **`GET /api/models` advertised `groq`/`mistral` but the installed pydantic-ai-slim extras couldn't run them** — `twomarkdown/server/models.py:CLOUD_PROVIDER_ENV_VARS` listed all six cloud providers, but `pyproject.toml` requested plain `"pydantic-ai>=1.52.0"` with no extras, which resolves (see `uv.lock`) to `pydantic-ai-slim[anthropic, cli, evals, google, logfire, mcp, openai, web]` — no `groq`, no `mistral`. Converting with a `groq:`/`mistral:` model id raised `ImportError` inside Docker at `pydantic_ai.providers.infer_provider_class(...)` time, after the catalog had already told the picker the model was fine. Fixed by changing the spec to `"pydantic-ai[groq,mistral]>=1.52.0"` (via `make uv-add PKG="pydantic-ai[groq,mistral]"`, never editing `pyproject.toml`/`uv.lock` by hand) — `openai`/`anthropic`/`google` ship through pydantic-ai's own default extras already, `openrouter` rides the `openai` SDK, so neither needed anything added. Guarded by `tests/test_server.py::TestModels::test_cloud_providers_import_through_pydantic_ai`, which imports every id in `CLOUD_PROVIDER_ENV_VARS` through `infer_provider_class` so the catalog can never again outrun the installed extras. `resolve_model` (`twomarkdown/server/models.py`) also now reports `problems: ["sdk_not_installed"]` (new `ResolveProblem` literal, `twomarkdown/server/schemas.py`) instead of silently falling through to `no_api_key`/`unknown_price` if a provider's class ever fails to import again.

- **pytest segfaulted at interpreter teardown in the Docker test container, after the whole suite had already passed (was: "Should fix — pytest segfaults...")** — root cause found and fixed, not just contained. `tests/test_server.py`'s `TestSyncs` tests (and the two `TestJobs` pause/retry tests that create real background job threads) start real background threads — `syncs.py`'s `_Watcher._loop` (a `watchfiles.watch()` poll loop) and `jobs.py`'s `_run_job` — and the shared `_isolated_state` autouse fixture's teardown only did `jobs._jobs.clear()` / `syncs._watchers.clear()`: dropping the dict *references*, never actually calling `.stop()` (`syncs.py`) or setting `cancel_event` (`jobs.py`), let alone joining the thread. Any test that enabled a sync (`test_patch_flips_enabled_in_place`, `test_watcher_runs_a_job_on_a_new_file`) left its `watchfiles.watch()` thread running as a daemon for the rest of the process; reproduced in isolation with `make test-backend TEST="tests/test_server.py -k test_patch_flips_enabled_in_place"` alone (exit 139). A daemon thread still parked inside `watchfiles.watch()`'s native (Rust) polling loop when CPython starts finalizing the interpreter is torn down mid-syscall instead of exiting cleanly, which segfaults rather than raising. Fixed at the source: `syncs.py`'s `_Watcher.join()` (new) and `stop_all()` (new) actually join the thread after `stop()`; `jobs.py`'s `_Runtime.thread` (new field) is joined by `jobs.shutdown()` (new) after setting `cancel_event`; `tests/test_server.py`'s `_isolated_state` fixture teardown now calls `jobs.shutdown()` and `syncs.stop_all()` before clearing the dicts, so no thread from one test survives into the next, let alone to interpreter exit. `twomarkdown/server/app.py`'s `_lifespan` now also calls `syncs.stop_all()` / `jobs.shutdown()` on shutdown, so `make app` exits cleanly for the same reason. `ulimit -c 0` (see the `run_uv_test` macro in the `Makefile`) is kept as belt-and-braces against a core file, not as the fix.

## Checked and clean

- **LibreOffice in the image** — `.doc`/`.ppt` (and related) convert via `soffice` in `docker/backend.Dockerfile`.
